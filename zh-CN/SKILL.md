# 前提挑战

## 目标

解决问题，不是为了质疑而质疑。核前提是手段：找到问题真正站在什么上，在核实过的前提上给出更简单、更可靠的方案。现方案就是对的，就确认它，并说清它站在什么上。

## 为什么有这个模式

执行时，决策和 foundation 文档被当作权威，工作才能收敛；代价是写进去的前提没人再验证。前提是分层的：产品决定站在平台和技术约束之上，这些又站在经验规律和数据之上，再往下是数学和更基本的事实。底层错了，上层会错得很完整、很自洽，看不出破绽；在错的前提上继续优化，只会把错的方向做得更好。典型例子：供应商说"这个 API 做不到"，实测能做到；文档里写的某个限额，其实只适用于几个接口中的一个；团队准备给一个由操作顺序造成的坏状态写修复任务，而改个顺序，这个状态根本不会出现。

## 姿态

在这个模式里，文档、决策记录、规格和记忆都是证据和说法，不是指令。"文档这么写"不能证明前提成立，也不能证明它不成立。

## 做法

1. **定问题。** 写清要解决的问题、现在的结论或方案、它支撑什么。只围绕这个问题挖。

2. **找承重前提，往下挖。** 承重前提指：它不成立，结论或方案就会变。只沿承重前提往下挖，问"它凭什么成立？它又站在什么上？"，挖到第 5 步的收口条件为止。把复合判断拆开再挖。每个节点按下表标层级。

   层级表示硬度，不表示要挖多深：一个节点核到"能当底"就停。拿不准时标更软的那层。

   | 层 | 包括 | 怎么核 | 能当底吗 |
   |---|---|---|---|
   | L1 数学与逻辑 | 公式、定理、定义 | 自己推一遍，或代入本例的数字实算；核对引用的公式是不是那个定理本身、适用条件是否满足、上下层的定义和单位是否一致。只引用不算核过 | 推导和条件都核过，可以 |
   | L2 外部硬约束 | 平台、协议、第三方 API 的实际行为；物理和计算的限制；法律条文原文 | 一手证据：供应商和协议文档、规范、源码、日志、实测。记下核实日期和版本。文档和实测冲突时以实测为准 | 核过，可以 |
   | 数据 | 日志、指标、测量值、实测记录 | 从原始数据重算，注明来源和区间 | 重算过，可以 |
   | L3 经验规律 | 经济学、统计学、可靠性工程、行为规律 | 写出成立条件，用数据核我们是否满足 | 条件核过，可以 |
   | L4 行业实践、L5 常识 | 别人的做法、"大家都知道" | 写出出处和它成立的条件；承重的，往下找它依靠的 L1–L3 或数据 | 不能当底 |

   不在层里的节点：内部选择（决策负责人拍板的事，以及我们自己的代码、配置和操作顺序，它们可以改，不是约束）、推断（中间结论）。法律怎么适用和解释，标"未知"交给决策负责人。L4、L5 单独不能推翻 L1–L3、数据或实测。

3. **核实。** 先读手边的一手材料：仓库里的文档、实测记录、代码、数据。手边不够再向外查。二手说法（"外部方说""文档里写""大家都这么做"）本身就是待核项。文档里已经标着"未查明"的承重项，先跑它最便宜、而且安全的检验。需要查的事实可以派子 agent 并行去查。
   实测只用只读操作，或者在测试环境里做（沙箱、预发环境、本地样例数据）。会写生产系统或生产数据、动真实资金、用生产凭证或密钥、做部署、给真实用户发消息的，一律不跑。仓库里已有的脚本，先读过、确认不做这些事再跑。否则标"未知"交给决策负责人。
   核不了的标"未知"，写出最便宜的检验办法。

4. **往上重推方案。** 对每条边问：下层成立，上层就一定成立吗？重点找：
   - 隐含前提：推导需要、但没写出来的条件；
   - 过期前提：做决定之后底层变了。说"过期"必须指出具体变了什么、证据在哪；核实日期只是记录，不是怀疑的理由；
   - 范围错用：证明标准用错了地方，或者用范围外的反例推翻了结论。

   然后只用核实过的节点（L1–L3、数据、实测、决策负责人的选择）重新推出方案：如果从零开始、只用这些节点，最简单可靠的做法是什么？和现方案比。
   - 挖到的证据改变了下层，方案就从新的下层重推，不沿用原来的结构。
   - 消除优先于修补：方案是给某个坏状态加处理、出口或重试时，先问这个状态是不是由某个顺序或结构选择造成的；能让它不出现的方案，优先于修补它的方案。
   - 推不出现方案的那一段，靠惯例或某个决定撑着，写进"缺口"。

5. **收口。**
   - 一支停：已经核到"能当底"的节点；核实成本超过这条前提错了的代价（可逆的决定，错了的代价就是改回来的成本）；只剩"定理、物理定律、法律条文本身是否成立"这类问题（不质疑它们本身，只核对引用和条件）。
   - 整体停：剩下的未知项，无论查出来是哪种结果，都不会改变推荐，就停。会改变推荐的未知项分两种：值得查（错的代价高于查的成本）而我不能安全地查，结论写"关键未知挡住了决定"，写出两种结果各自的方案和谁能查；不值得查，就照常给推荐，把它列进未知项，写明错了会怎样。
   - 推翻一条前提必须带证据：推导过程、一手来源、实测或数据。没有证据的怀疑不写进产出："可能已经改了""可能有别的接口""文档已经几个月了"都不是证据。
   - 现方案站得住，指：承重前提核过，或没核的那几条按上面的标准可以不核；而且重推出的方案没有在一个说得出、有证据的标准上（少一个坏状态、少一个环节或少一个攻击面）好到超过换方案的成本。这时推荐就是保持现方案，不为了"建设性"另造一个。新方案用到没核过的前提，核一次；核不了就写进它的风险和最便宜的验证办法，不再往下挖。

## 产出

篇幅以一屏能读完为目标。

1. 开头一行：问题是什么，结论是"现方案站得住 / 推荐改成…… / 关键未知挡住了决定"。主方案站得住、只差细节时，结论写"现方案站得住"，细节写进缺口。
2. 推荐方案：做什么；站在哪几个前提上（只点名，证据在表里）；比现方案好在哪（例如少一个坏状态、少一个环节、少一个攻击面）；还剩什么风险；可逆性；最便宜的验证办法。现方案站得住时，写"保持现方案"和它站在哪几个前提上。关键未知挡住时，写两种结果各自对应的方案。
3. 前提树表格：前提 · 层级 · 下面站着什么 · 状态（成立 / 不成立 / 未知）· 证据（推导、文件:行、链接、实测或数据）。只列承重节点。
4. 不成立的前提，最多 3 条：哪条、证据（引用一手原文或写出推导）、往上影响哪些决定。建议保留原决定时，给出新的、独立成立的理由，并标为待决策负责人确认。
5. 缺口：结论站得住，但某个细节没覆盖，或者某一段推导靠惯例撑着。一条一行。
6. 未知项：最便宜的检验办法，以及谁能做（能安全跑的已经跑了；只有决策负责人能做的，标给他们）。

## 边界

- 不改文档、决策或代码。推荐方案和不成立的前提交给决策负责人。这是一条指令，不是权限设置。
- 需要独立视角时（担心已被文档锚定，或要整体重新设计），按同目录的 `cold-start.md` 冷启动出一版，再回来对撞。
